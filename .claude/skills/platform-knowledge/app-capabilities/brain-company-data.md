# Brain: company data

[flag: brain-enabled]. If the rail has no **Brain** row (under **New app**), it isn't enabled for this account.

## What it is

- Brain brings data from the company's business systems (CRM, ERP, support desk, databases, file stores) into the account's own private data warehouse, so apps can use it.
- Each synced table or folder is a **data asset**.
- Each account has one Brain, opened from the **Brain** row in the platform rail (it is set up the first time someone opens it). It isn't listed in **My apps**. Each account can only ever read its own data.

## Who can do what in Brain

- Brain has two levels of access. **Can manage** and **Can build** are the same in Brain.
- **Can access**: see Brain's sources, tables, syncs and which apps use them, without changing anything, and use **Sync now** on a company table in an app. Where something needs doing (a source to reconnect, nothing connected yet), the page says to ask someone who can manage Brain.
- **Can manage** or **Can build**: everything above, plus connecting any source (the featured systems, **Browse all sources** and **Add a source**, including another connection to a system already connected), **Reconnect**, **Rename**, **Delete source**, **Choose tables** and **Edit tables**.
- Whoever opens Brain first sets it up and gets **Can build**. Opening Brain doesn't make anyone else a member: they see **Ask a Brain admin for access** until someone who can manage Brain adds them.
- **Adding people to Brain and changing their role**: someone who can manage Brain clicks **Settings** at the top of Brain home. It opens **Brain members** over the page: **Add by email** adds someone from the account (then pick their role), and the role badge or the **⋯** on a person's row changes their role (**Can access**, **Can manage**, **Can build**) or removes them. **Done** closes it.
- Controls someone can't use aren't shown. If an action is refused anyway, the message says what's needed, e.g. "You need Can manage access to Brain to connect or reconnect a source. Ask a Brain admin for access."
- A role decides what someone can change, not what they can see: everyone, Can build included, sees only the connections and tables they're on (see Who can use each connection and table).

## Who can use each connection and table

- A connection, table or saved query set up before access lists has no list yet, so everyone in the account can use it, as before. Its list says "Everyone in the account can use this connection"; a Brain manager clicks **Edit access** (it starts with everyone in Brain) and narrows it to set its first list. There's nothing to recover on one of these.
- Each connection has an access list: the people who can use it. Being on it means seeing the connection in Brain, syncing its tables into your apps, and starting with access to each new table it syncs. Only people in Brain can be added; adding someone to Brain is a separate step.
- **Connecting a source**: the **Choose what apps can see** step also asks **Who can use {source}**, starting with the person connecting it. Add people with **Add people from Brain**, remove them with the **×** on their row, then **Share N tables**. At least one person who can manage Brain has to stay on the list.
- **Changing it later**: a source's page has an **Access** tab. **Who can use this connection** lists everyone on it with their Brain role. A Brain manager (**Can manage** or **Can build**) who is on the list clicks **Edit access**, adds or removes people, then **Save changes** (or **Cancel**). Anyone else sees the list read-only: "Only a Brain manager on this list can change it."
- The last person on a list who can manage Brain can't remove themselves: "You're the last Brain manager on this list. Add another before removing yourself."
- **Each table has its own list.** A synced table or file folder starts with its connection's list, copied once when it's created; after that, changing one doesn't change the other. On the **Access** tab, **Synced tables** lists the connection's tables with how many people can read each; click one to open its list, edited the same way.
- **Saved queries**: Brain home has a **Saved queries** tab. Each saved query starts with everyone who could read all of the tables it's built from. Reading one needs both its own list and access to every table it's built from. In its list, a person a table blocks shows "Can't see {table}", and a Brain manager can turn on **Override** for them: they can then read the saved query without access to that table. A warning says what it does: "Gives {person} access to data built from {table}, which this person can't see."
- A search index has no list of its own: it follows the table it searches.
- Brain home shows only the connections you're on, and the **Tables** tab only their tables.
- **Recovering access**: an account admin always can. Brain home shows admins the other connections under **Connections you're not on**; open one, and its **Access** tab offers **Recover access**, which adds you to the list. It works the same in a table's or a saved query's list. Someone who isn't an admin asks a Brain manager on the list.
- Opening a connection you're not on shows only its **Access** tab. An account admin sees **You're not on this list** with **Recover access**; anyone else sees "You don't have access to this connection, so its tables and syncs are hidden. Ask a Brain manager on its list to add you."

## Connecting sources

- With nothing connected, Brain opens on **Connect your company's data**: pick one of the featured systems, or **Browse all sources**. Once something is connected, use **Add a source** at the top of Brain.
- **Add a source** lists every system, searchable and grouped by category. Picking one connects it straight away: sign in to it in a new window, or fill in a short form (databases, ERPs, or a Drive folder link). A **Name for the new one** is asked only when the same system is already connected.
- Then **Choose what apps can see**: every table starts ticked; untick anything apps shouldn't read, then **Share N tables**. Leaving this step without sharing keeps the source connected with nothing shared; its card says **No tables shared yet** and opens the step again. To remove a source from this step (for example when its tables couldn't be read), use **⋯ → Delete source** next to the close button.
- The catalogue includes HubSpot, Salesforce, Zendesk, Gmail, Google Drive, Postgres, MySQL, Snowflake, S3, Priority and SAP Business One, and more. It grows over time.
- The same system can be connected more than once, e.g. two HubSpot portals.
- An app's own tables are never added by hand. The first time Ella works with Brain data in an app, that app is connected automatically and listed in Brain as a source named after the app. Its tables then sync and show as data assets like any other source's. To sync an app's data into Brain, ask Ella in that app. An app can only sync its own tables, not another app's.

## Choosing what apps can use

- Brain home has two tabs. **Sources** lists each source as a card with its sync status (e.g. "Synced 5 minutes ago · every hour") and how many tables it shares; click a card to open the source. **Tables** lists every table shared with apps across all sources, with its source, column count and how many apps use it; search by table or source name, and click a table to open its source. A source sharing everything can take up to a minute to list the first time.
- A source's page has three tabs. **Tables** (the default) shows the tables shared with apps, how many there are, and how many apps use each. **Syncs** lists the source's recent syncs (when, how much, or why one failed). **Used in** lists the apps that use this source's data and which tables each uses; click an app to open it.
- On **Tables**, to change what's shared click **Edit tables**, tick or untick tables (search, **Show all** / **Hide all**, **Columns** to peek at a table's columns), then **Save changes** (or **Cancel**). Only ticked tables are offered to apps and to Ella. A source sharing nothing yet shows **Choose tables**.
- Sharing a table doesn't sync it. A table syncs once an app asks for it.
- Unticking a table an app already uses doesn't break that app: it keeps syncing. Only new requests for it are blocked.
- If Ella says some data "isn't available to apps", the account owner can tick it in Brain on that source's page.
- The **⋯** menu on a source's page has **Reconnect**, **Rename** (changes the name shown in Brain and apps; tables keep their names) and **Delete source**. A source that isn't connected also shows a **Reconnect** button under its name.
- **Reconnect** works for every source and keeps its name and tables: sign-in sources open the system's sign-in window again; form sources (databases, Priority, SAP Business One) open a dialog to re-enter the credentials, which are stored encrypted and never shown again.

## Syncing

- Each sync runs **Only when I ask** or **On a schedule**. Scheduled syncs default to hourly and run at most every 5 minutes. The first sync starts right away.
- When several apps need the same data, the most frequent schedule wins. Blocks warns when a schedule is about to change.
- You can pick which columns to sync.
  - Row filters only work for some systems (Priority and SAP Business One).
  - Rows that stop matching a filter aren't removed.
- A schedule belongs to the connection, not to one table: every table synced from that connection follows it.

## Adding company data to an app

- Company data is added to an app the way an integration is. Ella asks for it the first time the app needs company data: a **Company data** card in the chat ("Lets this app read the company data in Brain.") with **Use company data** and **Cancel**.
- **Use company data** adds it straight away. There's no account to sign in to and no connection to pick: it's the account's own Brain, shared with everyone who uses the app. **Cancel** tells Ella to build without it.
- Adding or removing it takes both: being able to build the app, and a role in Brain. Without a role in Brain, it fails with "You don't have access to Brain"; ask someone who manages Brain to add you.
- Once added, the app's **Settings → Integrations** lists it as **Brain** ("Your company's data, ready for this app") with a **Connected to Brain** badge. Builders also see **Open Brain** beside the badge, and **Remove from app** in the card's **⋯** menu. Removing it keeps the tables and saved queries the app already has; ask Ella to add company data again.
- The account's allowed-integrations list doesn't apply to it: it's the account's own data.

## In apps

- Each app lists the company tables it uses in its **Data** panel, in two groups after **Tables** and **Views** (followed by **Search indexes** when the app has one, then **Folders**): **Company data**, the tables synced from its sources (one row per table, with its source's logo where Blocks has one, such as HubSpot, and a table icon otherwise), and **Saved queries**, the tables its saved queries build. Click a group's name to fold or unfold it, like any other group. **Company data** is always there and says **No company data yet** until the app has a table; **Saved queries** shows only when the app has a saved query.
- To add tables, click **+** beside **Company data** (**Add company data**). **Add company data from Brain** lists the tables the account shares, by source: search, tick tables, then **Add N tables**. Tables the app already uses show **Added**. A source can take up to a minute to list the first time. Added tables update every hour; to change that, use the table's **Settings**. File sources (such as Google Drive) aren't listed here. A table that couldn't be added isn't marked **Added**, so it can be added again with **Add N tables**.
- A row's **⋯** under **Company data** or **Saved queries** is the same menu as any other row in the panel (such as **Ask in chat...**). **Edit query** and **Lineage** aren't in it: they're buttons in the table page's header, which has **Settings** (a synced table), **Edit query** (a saved query), **Lineage** and **⋯**. A synced table's **Settings** is in both: the row's **⋯ → Settings** and the gear in its page's header.
- Click a table to preview it: its first 20 rows, six columns at first (**Show all N columns** shows the rest). There's no row count. The header says which source it comes from and when it last synced (nothing, when that isn't known). A table just added shows **Waiting for the first sync** until its rows arrive; the page checks again on its own for about ten minutes, then offers **Check again**. A table that exists but holds no rows yet says **No rows yet**, and checks again the same way. **Not updating** means nothing refreshes the table any more; it can still be read. If the app isn't allowed to read the table, the preview says **This app can't read that table.**
- Under a table's header, **Built from** lists the tables a saved query reads, and **Used by** the saved queries that read this one (and its **Search index**, if the app has one); click one to open it. A name a query reads that isn't a table in this app shows as **unknown: <name>**.
- **Settings** (the gear button in a synced table's page header; **⋯ → Settings** on its row under **Company data**, or double-clicking the row, opens the same panel) opens the table's schedule in the builder's side panel; clicking the page's gear again closes it. It shows the source, the table's name and how often it syncs now (**Syncs**). Under **Updates**, pick **Only when I ask** or **On a schedule** (then the schedule), and **Save schedule**. The schedule is shared by every table from the same connection, and the most frequent one wins; when a change reaches past this table (the connection's schedule moves, or other apps use the connection), the panel says so and asks to **Change schedule** first. Saving also starts a sync. **Sync now** syncs every table from that connection right away; it's unavailable while a sync is already running or nothing syncs the table yet. It also needs access to Brain (**Can access**, **Can manage** or **Can build**); otherwise the panel says "Only people with access to Brain can sync now." A table that was saved but never requested (**This table was never requested**) is sent from the same panel with **Send request**.
- **Settings** changes only the schedule. To change which columns or rows a table takes, ask for the same table again from **Fetch data…**: the request is updated, not duplicated. A different table is a new request.
- **Lineage** (a button in every company table's header) opens the app's data map with this table's path highlighted: each source on the left (its logo or an icon, and its connection's name), then the tables synced from it, then the saved queries built on them — as many columns as queries are built on other queries — joined by lines. A table the app made searchable has a **Search index** card just right of it, which says **Searchable**, **Not searchable yet** or **No longer searchable**; click it to open the index. Each table shows where it stands: when it last synced or was built (**Synced 5 minutes ago**, **Built 5 minutes ago**), or **First sync running**, **Last sync failed**, **No sync recorded yet**, **Waiting for the first sync**, **Not updating**, **Never requested**, **Last run failed**, **Waiting for data** or **Not deployed yet**; **Checking…** while it's being read, and **Status unknown** if it can't be. A warning icon on a saved query means it reads a name that isn't a table in this app.
  - Hover a table or source to highlight everything it's built from and everything built on it; the rest dims.
  - Click a table to open its page (the map closes).
  - Drag to move around. The controls beside the map's title zoom out (**−**) and in (**+**), with the zoom level between them; **Fit** shows the whole map and **100%** goes back to full size.
- Click a saved query to preview it the same way: its first 20 rows. Its header says **Saved query** and when it was last built; **Built from** under it lists what it reads. **Edit query** (in its header) opens the **dbt project** editor on that query's file, over the table's page; closing the editor goes back to the table. Its preview appears once the query has been deployed successfully; until then the page says why (**Not deployed yet**, **Last run failed** or **Waiting for data**) with **Edit query**, where **Deploy** builds it. A query a deploy built whose table can't be read yet says **Not built yet**. One that built and returned nothing says **No rows yet**. Every link to a saved query (a chat mention, an activity row, search) opens this page; there is no separate saved-query page.
- To write a new saved query, open the **dbt project** and add a file under **models/** with **New file** (`models/<name>.sql`); with no files yet, **Create a saved query** opens **New file** already in models/. Edit an existing one with **Edit query**.
- **Removing a table.** Blocks system admins have **Delete** in a row's **⋯**, which withdraws the table's request first (if that fails, the table stays and an error says why). Everyone else removes a table or deletes a saved query by asking Ella in that app (or manages the source in Brain). Removing a table from an app stops its data reaching the app; the table stays in Brain. If that happens while its page is open, the page says **This table isn't in this app anymore**, with **Back to company data** (or, for a saved query, **This query was moved or deleted**, with **Back to company data** and **Open in dbt project**).
- With nothing shared in Brain yet, **Add company data** offers **Open Brain**.
- The **⋯** in a company table's header has **dbt project** and **Fetch data…** (with no table yet, they're in the **Company data** header: **dbt project** as a button, **Fetch data…** under **⋯**). **Fetch data…** is the full request form. Use it for a file source (such as a Google Drive folder, which **Add company data** doesn't list), or to choose columns, row filters and a schedule before the first sync: pick a **Data source** and the streams you need, then **Review** and **Apply**. A file source the app already reads isn't listed in the **Company data** group.
- There is no **Data assets** section any more. An old **Data assets** link opens **Company data**; an old link to one table's request opens that table with its **Settings** panel; an old link to a saved query's page opens its table's page, and an old new-query link opens **Company data** with the **dbt project** open.
- The **dbt project** shows every file behind the app's saved queries, with its code. Open it from **⋯ → dbt project** in a company table's header (or the **dbt project** button when the app has no table yet), or **Edit query** on a saved query (it opens on that query's file).
  - Saved queries are the files under **models/**, one each: `models/<name>.sql`, and the file name is the table's name. Macros, tests, seeds and docs sit in folders of their own.
  - Click a file to see its code. Edit it, then **Save** (or Cmd/Ctrl+S); **Save all** under the unsaved count saves every edited file.
  - **New file** adds a file by its path. Only .sql, .yml, .yaml, .md and .csv files can be added; a model must be `models/<name>.sql` with a lowercase name of letters, digits and \_, not already used by another table in the app.
  - A file's **⋯** has **Ask in chat...** and **Rename...**. Renaming a model renames its table on the next deploy. A model can't be renamed out of models/ ("Models stay in models/"). Files can't be deleted here; ask Ella.
  - Files under **Generated** (the project and profile settings, the list of tables the app can read, the README) are rewritten on every deploy and are read-only. Their paths, the generated naming macros under macros/, and dbt's own folders (target/, logs/, dbt_packages/) can't be used for new files.
  - **Check** compiles the whole project against the real data without building anything. **Deploy** builds every saved query. Both need every edit saved first.
  - Files can't be added, renamed or saved while Ella is working.
- **Copying a company table into the app** makes it the app's own editable table, kept in sync on a schedule. Use **⋯ → Copy into this app…** in the table's page header, or ask the chat. The dialog shows the new table's name (editable), its columns, the column that identifies a row (**Key**; when none is found, tick one and **Use as key**), **Updates** (daily by default) and **Delete rows removed in Brain** (off by default), then **Copy table**. In a draft, the table exists only in the draft and starts syncing once the draft is made live and the chat next works on the live app; otherwise the first sync starts right away. Once copied, the same menu item shows the table, its schedule, its sync status once it syncs (**Waiting for the first sync**, **Synced … ago**, **Last sync failed …**) and **Stop syncing**, which stops updates and keeps the table and its rows (in a draft, it takes effect once the draft is made live). Only tables the app already reads can be copied. New Brain columns reach the copy only when it's copied again (ask the chat).
- Adding company data, changing a schedule and **Sync now** wait while Ella is working.
- Ella asks before requesting new company data, and never needs warehouse passwords.
- In the chat, company-data work (requesting a new table, writing a saved query) shows as a **Data engineer agent** step [flag: brain-enabled].
- Beside each saved query it writes, the chat writes `models/<name>.yml` in the **dbt project**: what one row of the table is and what each column means, and, for a query whose numbers the app reports, its semantic model (dbt's semantic layer): the entities it joins on, the dimensions its numbers are grouped and filtered by, and its measures and metrics. An app with metrics also has `models/metricflow_time_spine.sql` and `.yml`, a calendar (one row per day) the semantic layer needs, listed with the saved queries. They're saved with the table when it's deployed, so the app's agents can read what the data means and what can be measured. Edit the file in the **dbt project** like any other, or ask the chat to change it.
- **Apps can read company data but not change it.** Syncing an app's own tables into Brain is still allowed (see Connecting sources).
- **Company data an app reads from Brain is for signed-in members of the account; on a public app, its agent and its code actions are the exception.** A table copied into the app (**Copy into this app…**) follows the app's own table access (`sharing-and-access/data-permissions.md`), not this rule.
  - An external user (someone signed in who uses the account's apps but isn't a member of the account) gets none, and neither does a visitor who isn't signed in when a public app's workflow reads company data for them in a step that isn't an agent or a code action. Either way, the agent or workflow asking is told that Brain data is only available to (signed-in) members of the account, and that nothing was read, rather than getting an empty result. To give an outside person company data, make them a member of the account.
  - On a public app, the app's agent (and anything it runs) and the app's code actions read as the app's owner for a visitor who isn't signed in, also when a workflow runs them: the visitor gets answers from the owner's company data.
  - A scheduled workflow reads as whoever last edited its trigger, and a schedule set from the app as the person who created it. An app's agent reads as the signed-in person chatting with it in the app. Reached through one of its channels (email, WhatsApp or phone; see `app-capabilities/agents-and-channels.md`), it reads as the account member the channel runs as (usually whoever set it up), not as the person writing or calling: anyone who can reach it there, someone outside the account included, gets answers from that member's company data. **Who can reach this agent** limits who can message it.
- **Whose access an app reads with**: the person using it. An app's agents and workflows list, describe, browse files and search only what that person is on (a scheduled workflow, whoever last edited its trigger), and an app's **Company data**, **Saved queries** and **Search indexes** groups list only what the viewer can read. A SQL query an agent or workflow runs isn't checked against the lists: it can read any table in the account's Brain.
- **"You don't have access to `{table}`. Ask a Brain manager."** means the person using the app (or asking Ella) isn't on that table's list in Brain, or on the list of a table a saved query is built from. A Brain manager on that list adds them on the source's **Access** tab, or in the saved query's list on the **Saved queries** tab (or gives an override); an account admin can recover the list first. An app never shows empty results in place of this message.
- Ella has only the access of the person chatting with her: she lists and browses only the connections and tables they're on, and a saved query, search index or app table built on a table they can't read is refused when she saves it, with that table's name. She can't work around it; ask a Brain manager for access. A connection missing from what Ella offers may be connected but not shared with you.
- An app's own tables (its connection in Brain, named after the app) start with the app's users who are members of the account.
- Each query returns up to 1,000 rows and must finish within 45 seconds; big reports should summarise in the query.
- Text files from file sources can be read. PDFs, spreadsheets and images can be listed but not read.
- **Search**: ask the chat to make a file folder or a table searchable, and the app can find documents and rows by meaning, in any language (PDF, Word and slide text included).
  - It is set up on the live app. In a draft the chat only checks it; it starts once the draft is made live and the chat next works on the live app.
  - Indexing runs in the background, so results show up a few minutes later, not right away.
  - An app's agent searches what that app made searchable. Ask it to search across the account to include what other apps made searchable too.
  - A table can be searched only up to 2,000,000 rows. For a bigger one, the chat makes a saved query that narrows it (for example, to the last year) searchable instead. A table that grows past the limit later drops out of search until it is narrowed.
  - To stop searching something, ask the chat to remove it.
  - To see what an app can search, open its **Data** panel: the **Search indexes** group (after **Saved queries**, shown only when the app has one) lists each searchable table or folder by name. Click one to see its **Source** (click it to open that table), the columns it **Searches** (for a folder, **Every file, in full**), and the columns used for each result's **Title**, **Date**, **Tags** and **Row ID**, when set. The page says **Searchable by the app's agent**, **Not searchable yet** (it is set up on the live app the next time the chat works on it), or **No longer searchable**. **Lineage** in its header opens the data map on it, beside the table it searches (not for a folder). It's read-only: ask the chat to change or remove an index. The index's file is in the **dbt project** (**⋯ → dbt project**, under rag/).
- Saved queries update when the app's live version updates.
- A workflow can run when a sync **succeeds or fails**, e.g. to notify someone. It fires for the live app only.
